# Contributing

Thanks for your interest in improving `@tegroton/tegro-money`. The library is intentionally small — two helpers, a webhook verifier, plus types and tests. The contribution bar is therefore higher than for a typical SDK: the goal is to **stay minimal and obviously correct**, not to grow surface area.

## TL;DR

```bash
git clone https://github.com/TegroTON/ai-telegram-pay-miniapp.git
cd ai-telegram-pay-miniapp
npm ci
npm test
npx tsc --noEmit
```

If those four commands pass on a fresh clone, you have a working dev environment.

## Prerequisites

- **Node.js ≥ 20.** The CI matrix runs on 20, 22, 24. Node 18 is past LTS and is not tested.
- **npm ≥ 10.** Required for `npm ci` against the committed lockfile.
- No global tooling. Everything lives in `devDependencies`.

## Project layout

```
src/        Library code. Keep small. No I/O outside `client.ts`.
tests/      Vitest specs. One file per logical unit.
examples/   End-to-end runnable examples (grammY bot + Express webhook).
            Treated as integration smoke tests, not exported to consumers.
dist/       Generated by `npm run build` — never committed.
```

## What we accept

- **Bug fixes** with a failing test that demonstrates the bug.
- **Documentation** that matches the upstream HTTP API. Anything that contradicts the official docs gets rejected.
- **New endpoint coverage** when the upstream API exposes a stable endpoint we don't wrap yet. Open an issue first to confirm scope.
- **Test additions** that close uncovered branches in `client.ts` or `webhook.ts`.
- **CI / tooling** improvements that don't add complexity.

## What we don't accept

- **New runtime dependencies** unless absolutely unavoidable. The package currently has zero. Keep it that way.
- **Custom abstractions** on top of the upstream API (retries, queues, "smart" caching). Consumers can wrap the client themselves — we won't pick the wrapper for them.
- **Breaking changes** unless tied to a `0.x → 0.y` bump (pre-1.0) or a major release.
- **Feature flags** or experimental APIs. Either it ships and is documented, or it doesn't ship.

## Development workflow

1. **Open an issue** (or comment on an existing one) describing the change. Skip this only for trivial typos.
2. **Branch from `main`**. Name it descriptively: `fix/webhook-nonce-collision`, `feat/list-shops`.
3. **Write the test first** for bug fixes. The PR diff should show: test fails on `main`, passes after the change.
4. **Run the full check locally:**

   ```bash
   npm ci
   npx tsc --noEmit
   npm run build
   npm test
   ```

5. **Update the changelog.** Add an entry under an `## Unreleased` heading at the top of `CHANGELOG.md`. If the change is internal only (CI, tests, docs that aren't user-visible), note that in the PR description and skip the changelog.
6. **Open the PR.** Fill in the template. Link the issue.

## Commit message style

We use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

| Prefix | When |
| --- | --- |
| `feat:` | User-visible feature |
| `fix:` | User-visible bug fix |
| `docs:` | README / CHANGELOG / SECURITY etc. |
| `refactor:` | Code change with no behavioral effect |
| `test:` | Tests only |
| `chore:` | Build / lockfile / housekeeping |
| `ci:` | GitHub Actions / workflows |
| `deps:` | Dependency bumps (usually from Dependabot) |

Scope is optional and useful for larger files: `feat(client): add listShops`.

## Coding conventions

- **TypeScript strict mode** is enforced via `tsconfig.json`. Don't relax it.
- **No `any`** in exported types. Prefer `unknown` and narrow.
- **No `console.log`** in committed code. Use `throw` for fatal paths and let consumers log.
- **Constant-time comparison** for any signature check. The existing helpers use `crypto.timingSafeEqual` — keep it that way.
- **Format:** the repo doesn't enforce a formatter. Match the surrounding style.

## Tests

- We use [Vitest](https://vitest.dev/). One spec file per module.
- New public methods need at least: happy path, signed-request shape, error envelope, and one tampering rejection where applicable.
- Network is mocked via `vi.stubGlobal('fetch', …)`. Don't introduce real HTTP in unit tests.
- `npm test` must stay green on Node 20, 22, 24.

## Reporting security issues

**Don't open public issues for security problems.** See [SECURITY.md](SECURITY.md) for the private vulnerability reporting flow.

## Code of conduct

Be patient, be specific, and assume good faith. Reviewers sometimes ask the same question twice — that's because PRs to a security-adjacent library deserve more scrutiny, not because the PR is unwelcome.
